# Мої фінанси

Самодостатній навчальний застосунок для особистих фінансів українською мовою. Написаний на HTML, CSS і звичайному JavaScript. Сервер, обліковий запис і встановлення пакетів не потрібні. Інтерфейс і назва є власними; застосунок не пов’язаний із BudgetBakers.

## Запуск

Відкрий `index.html` у сучасному браузері. Усі файли мають залишатися в одній папці. Для перевірки чистої міграції відкривай оновлену сторінку за тим самим адресним шляхом, що й стару: `localStorage` прив’язаний до походження сторінки.

## Дані та обмеження

- Дані зберігаються в `localStorage` поточного браузера під ключем `my-finances-v2`. Паролі й дані демонстраційної форми реєстрації не зберігаються.
- Під час першого відкриття цієї версії застосунок один раз додає 12 прикладів витрат із реалістичними сумами (заправка, кафе, магазин, аптека, кіно та інші). Це працює і для вже наявних даних: вони залишаються, приклади не дублюються. Якщо видалити приклад, він не з’явиться знову після перезавантаження. У списку витрати показуються зі знаком мінус.
- Спосіб розрахунку й рахунок — різні поля: рахунок визначає, звідки списуються гроші, а спосіб розрахунку описує, як саме ти заплатив. Доступні готівка, картка, банківський переказ, телефон або годинник, онлайн-оплата, електронний гаманець та «Інше». Старі операції без цього поля показуються як «Не вказано».
- Каталог категорій розширено; він охоплює продукти, кафе, пальне, таксі, аптеку, кіно, комунальні послуги, підписки, освіту та інші потреби. Батьківський бюджет і фільтр враховують підкатегорії. Уже збережені категорії не змінюються, нові додаються один раз.
- При міграції старий ключ `expense-tracker-v1` не видаляється. Старий формат не мав дати операції, тому перенесеним витратам призначається дата першої міграції. Новий формат зберігається окремо.
- Суми ведуться в цілих копійках. Наразі облікова валюта — гривня (UAH). Автоматичних курсів немає.
- Під час імпорту CSV назва, сума й дата обов’язкові. Якщо колонки рахунку чи категорії не зіставлені, беруться перший активний рахунок і перша категорія відповідного типу. Для переказу потрібен рахунок отримувача, відмінний від рахунку відправника. Спосіб розрахунку експортується та імпортується; у старих файлах без цієї колонки він лишається невказаним. Невідомі назви рахунків, категорій, способів розрахунку й типів, а також очевидні повтори пропускаються; результат повідомляється після імпорту. Підтримуються CSV із комою або крапкою з комою як розділювачем. Дата має формат `РРРР-ММ-ДД`, сума — додатне число з не більш ніж двома десятковими знаками.
- Регулярні операції не створюються без дії користувача. Кнопка «Підтвердити» створює один запис на заплановану дату і пересуває наступну дату; «Пропустити» лише пересуває дату.
- Цілі заощадження мають ручний прогрес і не змінюють баланс рахунків. Бюджети рахують витрати за обраний період.
- У разі недоступного сховища або нестачі місця сторінка показує помилку. Для захисту від втрати даних регулярно робіть резервну копію JSON.

## Тести

Потрібен Node.js. Запуск без залежностей:

```powershell
node script.test.js
node finance.test.js
node --check script.js
node --check finance.js
node --check app.js
```

Тести перевіряють стару логіку домашнього завдання, міграцію, точність сум, баланси, фільтри, бюджети, повторення дат, резервні копії та CSV. Основні сценарії в браузері варто пройти вручну: додати дохід, витрату й переказ; перевірити баланси; перезавантажити сторінку; створити бюджет і регулярну операцію; експортувати й імпортувати копію.

## Структура

- `index.html` — розмітка розділів і форм.
- `style.css`, `enhancements.css` — основне та додаткове адаптивне оформлення.
- `finance.js` — модель даних, міграція та чисті розрахунки.
- `app.js` — відображення, форми, події, сховище й імпорт/експорт.
- `script.js` — демонстраційна форма реєстрації та сумісність із початковими тестами.
- `script.test.js`, `finance.test.js` — автоматизовані тести.

## Що потрібно для зовнішніх інтеграцій

Банківська синхронізація потребує ліцензованого провайдера Open Banking, серверної частини, захищеного зберігання токенів, згоди користувача й перевірки вимог провайдера. Справжня авторизація, спільний доступ і синхронізація між пристроями потребують сервера, бази даних, керування ролями та захисту приватних фінансових даних. OCR чеків потребує дозволу на фото, обробки зображень і перевірки розпізнаних сум. Актуальні котирування й курси потребують джерела даних із чіткою датою оновлення. Жодна з цих інтеграцій не імітується в локальній версії.

Наступний технічний етап: спершу вирішити, чи потрібна справжня багатокористувацька синхронізація; лише після цього обирати серверну архітектуру й провайдерів інтеграцій.
